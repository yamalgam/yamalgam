Each surface groups findings into a coherent concern area, not a category.M10 is a large, disciplined piece of work: a YAML-native jq engine built on jaq 3.0, a metadata-carrying value model, two emitters, twelve native filters, a jq-manual conformance corpus with an explicitly reasoned allowlist, and a CLI. The engineering underneath is good. YamlVal clone is genuinely O(1) — Data holds Rc<Vec>, Rc<YgMap>, Rc<str> — so jaq's constant cloning costs refcount bumps, not deep copies. The arithmetic and ordering semantics are jq-faithful and mutually consistent. The dependency tree is clean: no CVEs, no yanked crates, licenses inside policy, lockfile committed, toolchain pinned, one new build script and zero new proc-macro crates across the whole M10 subtree. jaq's module loader is left at its default rejecting stub, so include/import cannot touch the filesystem. Every one of the eleven deviations in the implementation-notes ledger was checked against the code and every one is accurate. The defects cluster in one place, and it is not the engine. It is the round trip back to YAML text. Three separate confirmed data-loss paths all share the shape "the in-memory value is right, the emitted text is wrong": a scalar containing a comma is emitted unquoted inside a flow collection and re-parses as two values; a node mutated through an alias keeps its alias_of and is re-emitted as *anchor, discarding the edit; a string emitted under --schema 1.1 comes back as a boolean. Each was reproduced against the built binary. Separately, --in-place persists its temporary file without ever checking that anything was written to it, so a filter yielding no output truncates the user's file to zero bytes and exits 0 — also reproduced. --in-place is the amplifier throughout: it takes emitter bugs that would otherwise be visible glitches on a terminal and writes them silently over the user's files. One resource bound is missing rather than wrong. The alias-expansion limit counts parser events, and the builder shares subtrees by Rc, so a YAML bomb is linear in memory and passes every limit — then both emitters walk that DAG as a tree. A 216-byte input produced 13.2 MB of JSON in testing, and --strict did not stop it. Nothing here is architectural. The value model, the jaq wiring, the conformance discipline, and the dependency hygiene are all sound and worth keeping as-is. The remediation list is a set of localized fixes concentrated in the emitter and in run_in_place, plus one decision about whether the public API should be readable before M11 starts consuming it.

The YAML Round-Trip Surface

The query engine computes the right value and the emitter then writes text that does not mean that value — three independent paths where a scalar's content is re-read as document structure or as a different type.

Quoting ignores flow context, so a scalar containing a comma splits into two values on re-parse

Enables: yg -i persists the temporary file unconditionally, so a filter yielding no output truncates the input to zero bytes
Related: needs_quotes treats only LF and TAB as unsafe, so CR and other control characters reach plain scalars, Output quoting is hard-wired to the 1.2 core schema, so a string emitted under --schema 1.1 re-reads as a boolean Effort: small12-mo commits
critical

needs_quotes takes only a &str, so it cannot know whether the scalar will land inside a flow collection. emit/yaml.rs::string has the Position in hand but consults it only to decide whether a literal block is allowed, never for the quoting decision. Inside a flow collection, , [ ] { } are structural, so a bare scalar containing any of them changes the document's shape when it is read back. Reproduced against the built binary at 27cf037: $ printf 'tags: [alpha, beta]\n' > t.yml $ yg -i '.tags[0] = "x,y"' t.yml ; echo $? 0 $ cat t.yml tags: [x,y, beta] $ yg --json '.tags | length' t.yml 3 A two-element list became a three-element list on disk, with exit 0 and no diagnostic. The value jaq computed was correct — yg --json '.tags[0] = "x,y"' renders ["x,y","beta"] — so the defect is entirely in the text. Flow position is reached two ways. Input-preserved flow style is one, as above. The other is -c/--compact-output, which forces every collection to flow, so an ordinary block-style document becomes injectable the moment a filter constructs a scalar (filter-constructed values carry meta: None, so no source style protects them).

Give the predicate the context it needs: change the signature to needs_quotes(value: &str, flow: bool) — or thread Position through — and when flow is true, additionally require quoting for any value containing , [ ] { }. Have emit/yaml.rs::string pass matches!(position, Position::Flow). Separately, tighten the SingleQuoted arm, whose guard is !string.contains('\''): when the value does contain an apostrophe it currently falls through to a bare plain scalar rather than single-quoting with '' escaping. The corpus round-trip test at tests/emit.rs:190 only exercises EmitOpts::default(), so neither the compact nor the flow-nesting path has any round-trip coverage — extend it to run each fixture through EmitOpts::compact() and sort_keys: true as well.

Related: String slice assignment rewrites content but leaves Meta.raw holding the pre-edit source text, YamlVal can be constructed and parsed from outside the crate but not read — no accessor reaches Bool, Int, Float, Seq or Map Effort: medium12-mo commits
critical

Meta.alias_of is documented as "referenced anchor name when this node came from an alias", but nothing binds it to the node's contents. All three in-place mutation paths in jaq_core::ValT — map_index (valt.rs:159), map_values (valt.rs:129), and map_range (valt.rs:265) — rewrite self.data and leave self.meta untouched. The YAML emitter then treats alias_of as authoritative: Context::alias_is_emittable (emit/yaml.rs:321) returns true once the anchor has been written, and Context::alias_text (emit/yaml.rs:328) emits *name in place of the node's actual contents. Reproduced against the built binary at 27cf037: $ printf 'a: &x {p: 1}\nb: *x\n' > al.yml $ yg --json '.b.p = 2' al.yml { "a": { "p": 1 }, "b": { "p": 2 } } $ yg -i '.b.p = 2' al.yml ; echo $? 0 $ cat al.yml a: &x {p: 1} b: *x The engine computed the mutation correctly — --json proves it — and the YAML emitter threw it away. Under -i that is what gets persisted, so the user's edit vanishes with a success exit and no output. The author already knows the invariant: YamlVal::set_anchor (value.rs:305-310) clears alias_of when an anchor is set, and explode_aliases (value.rs:397-402) clears both. Those are two ad-hoc enforcement sites for a rule the type does not encode, and the mutation paths honour neither.

Make identity metadata impossible to desynchronize from content rather than adding a third clearing site. Preferred: split identity out of Meta — keep presentation-only fields (tag, style, raw) there and move anchor/alias_of into the Data layer, e.g. a Data::Alias { of: Rc<str>, value: Rc<YamlVal> } variant — so any mutation that rebuilds data structurally cannot leave a stale alias behind, and alias_of on a mutated map becomes unrepresentable. If the flat shape must stay, funnel every write through a single YamlVal::data_mut() that clears meta.anchor and meta.alias_of before handing out &mut Data, and make the field unreachable any other way inside the crate. Add a regression test asserting .b.p = 2 over a: &x {p: 1} / b: *x round-trips through to_yaml with the mutation intact.

Enables: yg -i persists the temporary file unconditionally, so a filter yielding no output truncates the input to zero bytes
Related: Quoting ignores flow context, so a scalar containing a comma splits into two values on re-parse Effort: small12-mo commits
significant

The spec's r[output.yaml.quoting] is a MUST: "yg MUST NOT produce output that is ambiguous under the active schema." The emitter has no way to honour it. EmitOpts (emit/mod.rs:22-32) carries indent, compact, sort_keys and color — but no schema — and needs_quotes hard-codes TagResolution::Yaml12. Under --schema 1.1 the loader resolves yes/no/on/off/y/n as booleans on the way in, while the emitter decides quoting with 1.2 rules on the way out, where those words are ordinary strings. Reproduced against the built binary at 27cf037: $ printf 'a: "YES"\n' > s.yml $ yg --schema 1.1 '.a |= ascii_downcase' s.yml > s2.yml $ cat s2.yml a: yes $ yg --schema 1.1 '.a | type' s2.yml boolean A string became a boolean across one round trip. yg does print a warning whenever 1.1 mode is active, which is a partial mitigation — the user is told the mode is dangerous — but the warning fires on every 1.1 invocation and says nothing about this specific transformation, so it does not distinguish a safe run from a lossy one. With -i the retyped document is written to the user's file. This is not in the deviations ledger; note 8 defers only the # yg-schema: pragma, not schema-aware emission.

Add the active TagResolution to EmitOpts, thread it from commands/query.rs::loader_config into to_yaml, and have needs_quotes resolve with that schema instead of the Yaml12 constant. Add an emit test asserting that a string "yes" emitted under the 1.1 schema comes back as a string. Failsafe and json schemas are safe in the other direction (they only over-quote), so 1.1 is the case that needs the fix.

JSON emission stringifies non-string mapping keys via Display, silently colliding with real string keys

Effort: small12-mo commits
significant

YAML mappings admit any resolved value as a key, and YamlVal's PartialEq and Hash keep Data::Int(1) and Data::Str("1") distinct (different hash tags at value.rs:644 and value.rs:646), so the IndexMap stores both. The JSON emitter flattens both to the same object key with no detection. Reproduced against the built binary at 27cf037: $ printf '{1: alpha, "1": beta}\n' > k.yml $ yg --json . k.yml { "1": "alpha", "1": "beta" } RFC 8259 permits duplicate names, but every mainstream parser keeps the last, so alpha is gone the moment anything consumes this. The same collapse hits true/"true", null/"null", and 1.0/"1.0". It is not confined to --json: to_json also implements the tojson native filter (funs.rs:78) and ValT::into_string (valt.rs:322), which backs jq string interpolation, so "\(.)" over such a mapping is equally lossy. Collection keys go through Display and emit {a: b}, indistinguishable from a string key whose content is literally that text. tests/emit.rs:10 exercises this function but only for the non-colliding case.

Detect the collision instead of allowing it. Build the key strings first and, on a duplicate, either return an error (to_json would become fallible, matching how jq rejects non-string keys under -j) or disambiguate non-string keys with a reserved encoding the caller can round-trip. At minimum, warn on stderr from commands/query.rs when --json is asked to render a mapping with non-string keys, so silent loss becomes visible.

needs_quotes treats only LF and TAB as unsafe, so CR and other control characters reach plain scalars

Related: Quoting ignores flow context, so a scalar containing a comma splits into two values on re-parse Effort: small12-mo commits
moderate

A string with no source style metadata is emitted plain whenever needs_quotes returns false, and that predicate rejects only \n and \t in the control range. yamalgam-scanner/src/reader.rs:70 documents that a bare \r is normalized to a newline, so a carriage return inside a plain scalar becomes a line break on re-parse. Confirmed reachable: printf 'a\rb\n' | yg -R . emits the CR byte literally (verified with od -c). -R builds values through YamlVal::str with meta: None, so no style preservation can intervene. The same gap applies to any filter-produced string, since arithmetic (ops.rs::value), resolve/resolve_as (value.rs:250) and the jaq constructors all return meta: None. Two further consequences. \x1b reaches an interactive terminal unescaped, so ANSI/OSC sequences in untrusted input become terminal control — quote_double would have escaped them, the plain path does not. And needs_quotes does not flag U+0085 (NEL) or U+2028/U+2029, which are line breaks under YAML 1.1; yg ships a --schema 1.1 mode advertising interop with exactly those consumers. quote_double itself escapes only below 0x20, leaving DEL and the C1 range literal even in the quoted path.

In needs_quotes, replace the two trailing contains checks with a single scan: value.chars().any(|c| c.is_control() || c == '\u{85}' || c == '\u{2028}' || c == '\u{2029}'). Keep the \n special case ahead of it so literal blocks are still chosen for newline-only strings. In quote_double, widen the escape arm to c if c.is_control() || ('\u{7f}'..='\u{9f}').contains(&c) using \uXXXX, since \xNN cannot encode above 0xff. Add round-trip tests for CR and ESC.

String slice assignment rewrites content but leaves Meta.raw holding the pre-edit source text

Related: Mutating through an alias keeps alias_of, and the emitter re-emits *anchor, silently discarding the edit Effort: small12-mo commits
moderate

Meta.raw is documented as "raw scalar text before schema resolution" and the builder populates it from the source event (build.rs:202). map_range on a Data::Str splices new content in and returns self with meta untouched — the test at valt.rs:560-573 asserts precisely that metadata survives, so this is intentional for style and incidental for raw. Two public behaviours then read stale text. YamlVal::raw_text (value.rs:212) prefers meta.raw over the string content, so after .a[0:1] = "J" on a: 'hello', the raw filter returns "hello" for a node whose value is "Jello". YamlVal::resolve_with (value.rs:239-249) also prefers meta.raw, so resolve and resolve_as re-resolve the original scalar rather than the edited one — a spliced "5" that now reads "true" still resolves as the old text. Full replacement (.a = "true") is unaffected, because it installs a fresh YamlVal with meta: None. Only in-place edits desynchronize, which keeps this narrow — but it is the same root cause as the alias finding: Meta describes source provenance and nothing invalidates it when the value stops coming from that source.

Clear meta.raw (and meta.tag, which likewise describes the source scalar) whenever a scalar's content is rewritten. If the data_mut() funnel proposed for the alias finding is adopted, this falls out for free. Alternatively drop the meta.raw preference from resolve_with so resolution always runs over current content.

This is the surface that matters most and it is the least finished. The emitter was built as an M10 stopgap ahead of the real serializer in M13, and it shows: quoting is decided by a context-free predicate that cannot see flow position or the active schema, and identity metadata is trusted over content after mutation. All three failures were reproduced against the built binary. None require an adversarial filter — the identity filter plus ordinary input is enough for two of them. The fixes are localized (a Position parameter, a schema field on EmitOpts, a mutation funnel that clears stale provenance) but they are not cosmetic, because -i writes the result to disk.

The In-Place Editing Surface

run_in_place is correctly atomic against crashes and correctly rolls back on error, but it never checks that the filter produced anything before renaming the temporary file over the user's document.

critical

run_records writes only from inside its visit closure, which the engine calls once per filter output. A filter that produces no output for a document writes nothing, and that is not an error — run_records returns Ok(None). Nothing between the run and the persist inspects file_last or the temp file's length, so the empty file is flushed, synced, chmod'd and renamed over the user's document. file_last.is_some() is checked, but only after the persist has already happened. Reproduced against the built binary at 27cf037: $ printf 'enabled: false\nname: production\nreplicas: 3\n' > config.yml $ wc -c < config.yml 44 $ yg -i 'select(.enabled)' config.yml ; echo $? 0 $ wc -c < config.yml 0 select() is the ordinary jq idiom for conditional output; it yields nothing whenever the predicate is false. So this is document-driven, not merely operator error: a pipeline running yg -i '.[] | select(.enabled)' services.yaml destroys the file whenever the input happens to contain no enabled entry. The filter is correct; the input decides whether the file survives. The content is unrecoverable — the rename is the last step and there is no backup. -i also composes with flags that discard the input entirely. in_place is declared requires = "files" but conflicts with nothing, so yg -i -n '{}' config.yaml overwrites every named file with the null-input result, and yg -i --json . silently rewrites a .yaml file as JSON. tests/yg.rs:234-300 covers in-place success, permission preservation, multi-document input and hard-failure rollback — every case except zero output.

Track whether the visit closure ever fired for the current file (run_records already threads a first flag for exactly this shape) and refuse to persist when it did not: drop the temporary, leave the original untouched, and exit non-zero with a message. If truncation is ever legitimate, gate it behind an explicit --allow-empty rather than making it the silent default. Add conflicts_with = "null_input" to the in_place arg. Consider also skipping the rename when the output is byte-identical to the input, so -i becomes a no-op instead of a rewrite that discards comments.

Atomic replace renames over the path, so symlinks are replaced and hard links broken; only mode is preserved

Related: yg -i persists the temporary file unconditionally, so a filter yielding no output truncates the input to zero bytes Effort: small12-mo commits
moderate

std::fs::metadata(path) at query.rs:155 follows symlinks, so source_metadata describes the link's target — but temporary.persist(path) is a rename(2) onto the link path itself, which replaces the symlink with a new regular file and leaves the target untouched. Reproduced against the built binary at 27cf037: $ printf 'a: 1\n' > shared/real.yml && ln -sf shared/real.yml link.yml $ yg -i '.a = 2' link.yml ; echo $? 0 $ test -L link.yml || echo "symlink was replaced by a regular file" symlink was replaced by a regular file $ cat shared/real.yml a: 1 The edit landed on a new file at the link's path; the file the user believed they were editing is unchanged. Symlinked config trees are a common layout (overlay directories, Kubernetes manifest trees, /etc conventions). The same applies to hard links: every other name for the inode keeps the pre-edit content. The direction here is defensive against the classic symlink attack — yg does not write through an attacker-planted link into a privileged path — so the exposure is silent breakage of intentional links, not privilege escalation. Ownership is the second half: set_permissions carries mode bits only and the temp file is owned by the invoking user, so a root process running yg -i over a user's checkout leaves root-owned files behind. tests/yg.rs:277 covers the mode case only.

Call std::fs::symlink_metadata(path) first. If it reports a symlink, either resolve with canonicalize() and edit the target (documenting that choice) or refuse with a clear message — do not silently replace the link. On Unix, follow set_permissions with a chown to the source's uid/gid when the process has the privilege, and warn when it does not. Detect nlink > 1 and warn that the edit will break the hard link.

A mid-stream failure during yg -i leaves earlier files rewritten with no rollback and no report

Related: yg -i persists the temporary file unconditionally, so a filter yielding no output truncates the input to zero bytes Effort: medium12-mo commits
moderate

run_in_place rewrites files one at a time, persisting each before moving on. Every fallible step inside the loop propagates with ?, so a failure on file N aborts with files 1..N-1 already replaced and N+1.. untouched. Reproduced against the built binary at 27cf037: $ printf 'n: 1\n' > f1.yml ; printf 'n: [bad\n' > f2.yml ; printf 'n: 3\n' > f3.yml $ yg -i '.n = 99' f1.yml f2.yml f3.yml ; echo $? yg: f2.yml: unexpected StreamEnd, expected FlowEntry (,) or FlowSequenceEnd (]) in flow sequence 5 $ cat f1.yml ; cat f3.yml n: 99 n: 3 The message names only the file that failed. Nothing tells the user that a prefix of their argument list was already modified, so the natural response — fix f2 and re-run the same command — re-applies the filter to f1. For a non-idempotent filter such as .count |= . + 1, that double-applies silently. tests/yg.rs:293-300 covers the single-file case, where the guarantee does hold.

Either stage every file into a temporary first and persist only after all files succeed (a two-phase commit, which the tempfile-per-file structure already nearly supports), or keep the streaming behaviour and make the partial state explicit: on failure, report which paths were modified and which were skipped.

The Resource Bounds Surface

The loader's limits are enforced where the document is built and nowhere else, so a bounded in-memory graph becomes an unbounded walk at emit time and an unbounded allocation at mutation time.

The alias-expansion limit counts parser events, not materialized nodes, so both emitters expand the shared DAG unbounded

Enabled by: fromjson hard-codes moderate limits and uses the full YAML parser, bypassing --strict
Related: Emitters, Display, Hash and drop glue recurse over filter-constructed values with no depth limit Effort: medium12-mo commits
critical

Builder::node charges one unit against max_alias_expansions (10,000 under moderate, the CLI default) per Event::Alias, then resolves the alias by Rc-cloning the anchored node. The resulting graph is a DAG with shared subtrees, so a classic billion-laughs document costs O(source length), not O(expanded size), and passes every limit. Both emitters then walk that DAG as if it were a tree. emit/json.rs::write_json has no alias branch at all — it matches only on Data, so every alias is materialized unconditionally. emit/yaml.rs::alias_is_emittable emits *name only when the anchor was already written during this same emission; when it was not, the full expansion is inlined. Reproduced against the built binary at 27cf037, with a 216-byte input and six levels of 9-way aliasing: $ wc -c < bomb.yml 216 $ yg --json . bomb.yml | wc -c 13227921 $ yg --strict --json . bomb.yml > /dev/null ; echo $? 0 That is roughly 61,000x amplification, and --strict does not stop it — the strict profile tightens depth and alias-expansion caps, neither of which this trips. Each additional nesting level multiplies output by 9: measured on the same machine, seven levels (272 bytes) produces 143 MB and eight levels (307 bytes) produces 1.41 GB. The failure mode is OOM-kill of the process, which on a CI runner is a denial of service from a few hundred bytes of attacker-supplied YAML. Default YAML output is not safe either: yg '.g' bomb.yml selects a subtree whose descendants alias anchors defined outside it, so anchors_emitted stays empty and every level expands — 34 MB of YAML from the 272-byte input. --sort-keys breaks it a third way whenever sorting moves an alias ahead of its anchor; on a bomb whose keys are already in definition order -S changes nothing (328 bytes either way), but on one where sorting reverses that relationship it yields 39 MB from 272 bytes. The one safe case is the bare identity filter with YAML output over a whole document, where source order guarantees anchors come first — which is exactly the case the round-trip corpus test exercises.

Bound emission, not just parsing. Two changes, best applied together. (1) Give to_yaml and to_json an output budget — node count or byte count — threaded from LoaderConfig::limits, and fail with a Limit error rather than allocating past it. (2) Make to_json alias-aware the way to_yaml is: track visited Rc identities via Rc::as_ptr during the walk and error, or emit a repeat marker, when the same shared node is reached more times than a threshold. Identity tracking also fixes the --sort-keys and subtree-selection cases in to_yaml, which the current anchors_emitted name list cannot see.

Emitters, Display, Hash and drop glue recurse over filter-constructed values with no depth limit

Related: Assignment to a large sequence index allocates from the filter-supplied integer with no ceiling, The alias-expansion limit counts parser events, not materialized nodes, so both emitters expand the shared DAG unbounded Effort: medium12-mo commits
significant

Input documents are depth-limited during construction — Builder::node calls limits.check_depth (build.rs:93-96), and LoaderConfig caps depth at 64/256/1024 for strict/moderate/trusted. No such bound exists for values the filter itself builds. jaq evaluates reduce and foreach iteratively, so yg -n 'reduce range(100000) as $i (null; [.])' constructs a 100k-deep sequence without overflowing during evaluation. Every consumer of that value then recurses once per level with no limit: write_json here, Context::node -> block_collection -> sequence -> node in emit/yaml.rs:47-100 (the default output path, several frames per level), Display::fmt in value.rs:670-701, Hash in value.rs:636-662, Ord in value.rs:619-634, and deep_merge in ops.rs:29-46. The Emission Performance Surface

The value model is genuinely fast and the emitter is where the allocations are — a String per node, a String per line of indentation, a copy per scalar inspected, and a linear scan per anchor lookup.

moderate

The block path writes into a shared &mut String, which is the right shape. The flow path does not: fn inline(&mut self, value: &YamlVal) -> String (emit/yaml.rs:191) builds each nested value into its own String and then pushes that String into its parent's, so a value at depth d is copied d times on its way to the output. For a document rendered with -c, total copying is O(output_size * depth) rather than O(output_size). For a scalar that resolves as a string — the overwhelmingly common case — that means allocating a String containing the entire scalar, matching on it, and dropping it, purely to learn that it was a string. The cost is one allocation and one full copy per scalar emitted, so a document with N string scalars performs N copies of the document's total scalar bytes on top of writing them. This is on the default output path: every plain scalar in every emitted document goes through it. It compounds with the per-node String allocation above, since both run over the same data.

Add a borrowing or predicate form to the TagResolver trait — resolves_as_string(&str) -> bool, or a resolve_scalar_kind returning a lightweight enum — and call that from needs_quotes. The resolver already computes the discriminant before building the Value; this only avoids materializing the payload.

Emitted-anchor lookup is a linear Vec<String> scan run several times per node

Related: aliases and orphan_anchors never inspect mapping keys, so key anchors and key aliases are invisible Effort: trivial12-mo commits
moderate

anchors_emitted is a Vec<String> scanned linearly on every alias check, and the check runs per node during emission. For a document with A anchors and N nodes, emission is O(N * A) in string comparisons. Most real documents have a handful of anchors, so this is invisible in practice — but a generated document with thousands of anchors (Helm value trees and CI matrices both produce these) turns emission quadratic. The same shape appears in IdentityInventory (value.rs), which dedupes anchors with a linear Vec scan, making the aliases and orphan_anchors filters quadratic in anchor count. Those two filters exist specifically to audit documents with many anchors, which is the input that makes the scan expensive.

Replace both with a HashSet<Rc<str>> (or an IndexSet where insertion order is needed for output). The anchor names are already Rc<str> in Meta, so the set can share them without new allocation.

The CLI parses every document of every input file into memory before the filter runs

Related: -n/--null-input reads standard input to EOF before running, so yg -n hangs on a terminal Effort: medium12-mo commits
moderate

collect_inputs reads each source to a String and parses every document into a Vec of records before run_filter is called. Peak memory is therefore the sum of all input files plus their full parsed representations, even for a filter that inspects one field of the first document. jq streams: it parses one value, runs the filter, emits, and moves on, so its resident set is bounded by the largest single document rather than the whole input set. The practical consequences: yg '.name' **/*.yaml over a large repo holds every file in memory simultaneously, and yg 'first(.[])' huge.yaml pays for the entire document. It also means yg cannot be used on a stream that never ends — kubectl get -w -o yaml | yg . produces nothing, because collect_inputs is still waiting for EOF. Whether this is a design choice or an accident is not recorded anywhere; the spec does not commit either way.

Make the record source a lazy iterator that parses one document at a time and yields it, rather than a Vec built up front. The engine already consumes an impl Iterator<Item = Result<YamlVal, String>>, so the interface it needs is in place; the change is confined to collect_inputs and its callers. Note that -s (slurp) and -i legitimately need the whole set, so those paths keep the eager form. If streaming is not wanted, record the decision in the spec so the memory profile is a stated contract.

The headline question has a good answer: YamlVal clone is O(1) regardless of document size, and an alias shares its referent rather than copying it, so jaq's constant cloning is cheap and the core value model is the fast part of this crate. None of the findings here affect correctness, and for typical CLI documents none are user-visible. They are recorded because this is a workspace with a dedicated benchmark crate and an explicit performance identity — the emitter is currently the part that would show up in those benchmarks, and it is also the part slated for replacement in M13, which makes now the cheap moment to decide whether to optimize it or wait.

IdentityInventory::visit descends into sequence items and mapping values but never into the key node itself, even though the builder gives keys full metadata — build.rs:140 builds keys through the same node() path, so &anchored_key: v and *alias_key: v both carry anchor and alias_of. The consequences are wrong answers rather than errors. Both filters are advertised in README.md as auditing tools, which is exactly the use case a false positive breaks. Call self.visit(key, path) for each key before visiting the value, using a path representation that distinguishes key position from value position. Add a test with &k key: v and a second mapping whose key is *k.

Regex filters are backed by regex-bites, not the PCRE-compatible engine the spec promises

Effort: trivial12-mo commits
moderate

The regex surface is delegated wholesale to jaq-std 3.0.1, which depends on regex-bites (Cargo.lock:625-637); defs.jq only wraps the native matches builtin for match and scan. regex-bites is a finite-automata engine in the Rust regex family: no lookahead, no lookbehind, no backreferences, no possessive or atomic groups. jq 1.8 uses Oniguruma, which supports all of them. Every jq-manual example in the corpus passes, so the common cases — named captures, flags, g — are fine. But a user porting a real jq script containing (?=...), (?<=...) or \1 gets a runtime error rather than a result. That is at least a hard failure rather than silent degradation, which is the right direction. The problem is documentary: the promise in the spec is unqualified and the deviations ledger does not list it, so a user has no document telling them the limit exists. The unmatched-optional-capture difference is already allowlisted (tests/fixtures/manual-allowlist.yml:39-41), which shows the engine difference is known at the case level but not at the capability level.

Add a numbered entry to docs/spec/yg-spec-draft-01-implementation-notes.md stating that regex support is the regex-bites/RE2-style subset — no lookaround, no backreferences — and have draft 02 replace "PCRE-compatible" with the accurate constraint. Optionally mention the workaround in README.

This is the surface that came out best, and the discipline behind it deserves saying plainly: every one of the eleven entries in the implementation-notes ledger was checked against the code and every one is correct, and the jq-manual allowlist gives each expected failure an individual reason with a spec cross-reference. That is better conformance tracking than most shipped tools have. The findings below are all of one kind — behaviour that diverges from a documented promise and is not in the ledger. The fix for several is a ledger entry rather than code, which is cheap; the point is that the ledger is currently the project's strongest conformance artifact and these items are missing from it.

The crate implements two of jaq's own traits but pins jaq with a caret range that admits minor upgrades

Effort: trivial12-mo commits
advisory

valt.rs implements jaq_core::ValT and, separately, jaq_std::ValT — jaq 3.0 split the trait across two crates, and yamalgam-query implements both. Implementing a dependency's traits is a much tighter coupling than calling its functions: a new required method, a changed associated type, or a default-method signature change in any 3.x release is a compile break, and semver permits all of those on a trait that is not sealed and not #[non_exhaustive]-guarded. Nothing is broken today and it builds clean — but the caret has already been exercised. Cargo.lock:614-615 pins jaq-core 3.1.0, not 3.0.1; only jaq-std is still at 3.0.1 (Cargo.lock:624-626). So a minor bump on the crate whose traits this code implements has already been taken silently under this range. That strengthens the case rather than weakening it: the range says "any 3.x is fine" while the code's actual tolerance is narrower and unstated, and the next bump may not be as benign. Both trait impls are present and confirmed: jaq_core::ValT at valt.rs:22, jaq_std::ValT at valt.rs:395.

Decide deliberately and write it down. Either tighten to jaq-core = "~3.0" / jaq-std = "~3.0" so a minor bump is an explicit action, or keep the caret and add a comment in Cargo.toml noting that valt.rs implements jaq traits and that jaq upgrades need a compile check rather than a rubber stamp. Whichever, a CI job that periodically builds against the latest permitted jaq would turn a future break into a scheduled notification rather than a surprise.
