The Emitter and Expansion Surface

M10 makes yamalgam a producer of YAML as well as a consumer, and the metadata it preserves for fidelity can be replayed into output as structure the user never wrote.

YAML emitter writes node tags verbatim, allowing structure injection from a crafted tag

Related: Double-quote escaping omits DEL and C1 controls, emitting characters YAML forbids, A string of `...` is emitted unquoted, becoming a document-end marker Effort: small12-mo commits
significant

safe_tag is the only sanitizer between a node's tag metadata and the emitted document. It checks the tag's *prefix* but never validates the tag's character content, so any tag beginning with ! and containing no second ! is copied into the output verbatim by properties() (emit/yaml.rs:360-366), which then writes it ahead of the node in value_after_indicator (emit/yaml.rs:159-161) and node (emit/yaml.rs:65-71). A tag containing a line break therefore ends the current line and starts a new one at column 0 — attacker-chosen YAML structure inside a document the user believes yg merely reformatted. Two independent sources feed unvalidated text into that sink: 1. A malicious input file. The scanner accepts any non-whitespace, non-flow-indicator run after ! as a tag suffix (scanner.rs:1643-1651) and then percent-decodes it (decode_tag_uri, scanner.rs:2861-2878) with no re-validation of the decoded result. The document k: !x%0Ainjected%3A%20true v yields the tag !x\ninjected: true, which the parser hands through unchanged (parser.rs:540) and build.rs stores in Meta.tag (build.rs:197-203). yg . evil.yaml then emits: k: !x injected: true v — a new top-level key that did not exist in the input. With yg -i the injected structure is written straight into the user's file. 2. A filter. set_tag (value.rs:379-398) accepts an arbitrary string and stores it as the tag with no character validation, unlike its sibling set_anchor (value.rs:401-433), which enforces [A-Za-z0-9_-]+. A shared filter that appears to be a formatting pass can therefore write arbitrary text into an edited file. Even without a line break this is a corruption primitive: set_tag("x: 1") renders as !<x: 1>, a verbatim tag containing a space, which no conforming parser will read back.

Validate tags at both boundaries instead of trusting the prefix. - In safe_tag, reject or percent-re-encode any tag whose characters fall outside YAML's ns-tag-char / ns-uri-char sets (no whitespace, no line breaks, no control characters, no flow indicators). The safest form is to re-encode the suffix with percent-escapes on the way out, which is what the scanner decoded on the way in — that makes the emitter the exact inverse of decode_tag_uri and closes both sources at once. Returning None (dropping the tag) is acceptable as a fallback; silently emitting it is not. - In YamlVal::set_tag, apply the same character validation and return Error::str for a rejected tag, mirroring set_anchor's existing check.

explode_aliases materializes the alias DAG with no resource limits (Billion Laughs)

Related: Filter-constructed collections bypass the configured resource limits Effort: small12-mo commits
significant

The rest of the M10 pipeline treats Billion Laughs correctly. build.rs counts alias events against check_alias_expansions (build.rs:154-159) and shares the anchored value by Rc, so parsing a bomb is cheap; emit::validate_value re-counts alias expansions before rendering (emit/mod.rs:82-91); and the YAML emitter re-emits *anchor references rather than expanding them. The explode_aliases filter bypasses all of it. It walks the *logical* tree rather than the Rc DAG and constructs a fresh node for every reference, taking no limits argument and performing no checks. A classic nine-level, nine-way bomb parses within even --strict limits (81 alias events against a cap of 100) but expands to 9^9 ≈ 3.9x10^8 nodes here, exhausting memory long before the emitter's validate_value gets a chance to count anything. yg 'explode_aliases' bomb.yaml — the exact filter a user reaches for to normalize an untrusted file before committing it — is enough. Neither --strict nor the default moderate profile bounds it, because the only limit that would apply (max_alias_expansions) is never consulted on this path. A second, milder instance of the same gap: Display for YamlVal (value.rs:793-828) also walks the expanded tree with no limits, and jaq error construction formats values through it (for example Error::typ(self.clone(), "mapping") in merge_keys, value.rs:463), so a type error on a bomb value renders exponentially too.

Thread limits into the expansion. explode_aliases is invoked from funs.rs:187 where context_value.0.data().context.config.limits is already in hand — pass a &ResourceLimits plus a running expansion counter and node budget, return jaq_core::ValR<Self>, and fail with Error::str once check_alias_expansions / check_collection_size trip. Counting expansions on entry to each alias node (mirroring build.rs:154-159) is sufficient and keeps the error message consistent with the loader's. Separately, cap Display for YamlVal at the configured depth/output size, or truncate the rendered value in error messages, so error formatting cannot be turned into the same amplifier.

Double-quote escaping omits DEL and C1 controls, emitting characters YAML forbids

Related: YAML emitter writes node tags verbatim, allowing structure injection from a crafted tag, A string of `...` is emitted unquoted, becoming a document-end marker Effort: trivial12-mo commits
moderate

needs_quotes correctly forces double-quoting for these characters — char::is_control() covers U+007F through U+009F (value.rs:847) — but quote_double then writes them into the quoted scalar unescaped, because its escape arm only matches code points below 0x20. YAML 1.2's c-printable production excludes U+007F-U+0084 and U+0086-U+009F entirely, so yg emits a document that a strictly conforming parser must reject. yamalgam's own scanner is not such a parser and round-trips these values successfully — input.rs:124 states outright that "printable chars enforced by UTF-8 validation", and the scanner treats only \n and \r as line breaks — so the exposure is interoperability, not self-inconsistency. U+0085 (NEL) is the sharpest case: it is a legal character in 1.2 but a line break for libyaml, PyYAML, and every YAML 1.1 reader, so a scalar yg emits silently re-parses as a folded two-line scalar with different content in any of those consumers. Reachable without a hostile filter: yg -R -s . notes.txt on a file containing a U+0085 byte pair passes the character through append_input (commands/query.rs:519-538) unexamined — read_to_string only validates UTF-8, and str::lines only splits on \n. A fromjson input carrying a U+0085 JSON escape, and jaq string literals, are the other two paths.

Extend the escape arm to cover everything outside YAML's printable set, not just C0: escape \u{7f}..=\u{9f} as \xNN, and \u{2028}/\u{2029} as \L / \P (both are valid YAML double-quoted escapes). The cleanest form is to invert the test — escape anything that is not c-printable — so future additions cannot slip through. json_quote (emit/json.rs:100-118) has the same shape and should get the matching \u00NN treatment for consistency, though raw DEL is legal in JSON.

A string of `...` is emitted unquoted, becoming a document-end marker

Related: YAML emitter writes node tags verbatim, allowing structure injection from a crafted tag, Double-quote escaping omits DEL and C1 controls, emitting characters YAML forbids Effort: trivial12-mo commits
moderate

The indicator set covers every leading character that opens a YAML construct except ., and there is no positional check for the document-end marker. A string whose content is ... (or ... anything) is therefore emitted plain. In value position this is harmless — k: ... re-reads as the string. At Position::Root it is not: to_yaml sends a scalar document straight to scalar_node (emit/yaml.rs:175-198), so yg '.a' evil.yaml > clean.yaml where a: ... (plain style) writes a file whose entire content is ..., a document-end marker. Re-reading clean.yaml yields an empty document, not the string. The trigger requires the scalar to reach the emitter with plain or absent style: a quoted input scalar carries its NodeStyle through to string() (emit/yaml.rs:284-292) and is re-quoted safely, but a plain input scalar or a filter-constructed string (yg -n '"..."') is not. The same applies between documents in multi-document output, where run_records writes --- and then the bare marker (commands/query.rs:145-148), and under -i, where the file the user asked to edit becomes an empty document. The counterpart --- is caught only incidentally, by the - in the indicator set — which is the shape of the gap: the check is character-classifying, not context-aware.

Quote any scalar that would be read as a document marker in the position it is being written. Minimal fix: in needs_quotes, return true when the value is ... or starts with ... ; the Position::Root distinction is not worth threading through, and quoting it everywhere costs nothing. Add --- to the same test so the behaviour is explicit rather than a side effect of the - indicator.

Filter-constructed collections bypass the configured resource limits

Related: explode_aliases materializes the alias DAG with no resource limits (Billion Laughs) Effort: small12-mo commits
advisory

runtime_limits exists to carry ResourceLimits into jaq trait methods that do not receive RunCtx, and run_filter_with_null_input activates it for the whole run (engine.rs:227). But it is consulted at exactly three places: check_collection_size in the two map_index sequence-extension arms (valt.rs:202, valt.rs:266) and check_scalar_size in string multiplication (ops.rs:130). Every other constructor is unbounded. jaq compiles [ f ] to Ast::Arr(f) => box_once(f.run(cv).collect()) (jaq-core filter.rs:473), which lands in this FromIterator impl. [range(1e9)] therefore allocates a billion YamlVals and is killed by the OOM killer; reduce range(1e9) as $i ([]; . + [$i]) and map(.) over a large input are the same. --strict, which a user reasonably expects to bound a hostile workload, changes nothing here. Weighted as advisory because the input is a filter, which is code the user chose to run, and jq itself OOMs on [range(1e9)] — this is parity, not a regression. It is worth recording because the presence of runtime_limits and a --strict flag advertise a stronger guarantee than the code provides, and the distinct, input-driven case (explode-aliases-unbounded-expansion) is a real bug that lives in the same blind spot.

Either enforce or document. Enforcement is only partly available where it is most wanted: FromIterator::from_iter returns Self, as do YamlVal::seq (value.rs:182) and YamlVal::map (value.rs:191), so a check_collection_size at those sites has no error channel and could only panic, truncate, or set a deferred flag. Of the three call sites, only ValT::from_map (valt.rs:33, returning ValR<Self>) can propagate a failure directly. So: enforce in ValT::from_map, and for the Self-returning constructors either record a tripped-limit flag in a thread-local beside runtime_limits::ACTIVE and convert it to a YgError::Runtime after each output — the same shape this audit proposes for into_string — or accept that array construction is unbounded and take the documentation option instead. To document, state in the --strict help text and the spec that limits bound *input parsing and output rendering*, not filter evaluation, so --strict is not mistaken for a sandbox.

The Error and Program Flow Surface

The error architecture is typed and disciplined, but the runtime's growth bounds are enforced by convention at call sites rather than by construction, and one class of input error loses its type on the way out.

Recursive YamlVal traversals have no depth bound; only the Drop path is iterative

Related: runtime_limits guards string repeat but not concatenation or sequence growth Effort: medium12-mo commits
moderate

Every structural traversal of YamlVal outside the Drop path is naked recursion with no depth parameter and no ResourceLimits::check_depth call: explode_aliases (value.rs:505), PartialEq::eq (value.rs:698), Ord::cmp (value.rs:742), Hash::hash (value.rs:759), Display::fmt (value.rs:793), and deep_merge (ops.rs:29). The crate already knows deep value trees are a stack hazard - YgSeq and YgMap carry hand-written Drop impls that hand off to the explicit worklist in drop_values (value.rs:124) precisely to avoid recursive destruction - so the mitigation exists on exactly one path and nowhere else. Two ways to reach a value deeper than max_depth. First, from input: the builder's check_depth(depth) at build.rs:93 counts *event nesting*, not resulting value depth, and Event::Alias clones the anchored value without incrementing depth (build.rs:154-171). A chain of anchors ("a: &a0 [0]" / "b: &a1 [*a0]" / "c: &a2 [*a1]" ...) therefore yields a value tree as deep as the anchor chain from a document whose syntactic depth is 2. The only ceiling is max_anchor_count / max_alias_expansions (both 10_000 under moderate; max_anchor_count is None under --trusted with max_alias_expansions at 1_000_000). Second, from the filter, which this audit's scope treats as untrusted: "reduce range(200000) as $i (null; [.])" builds arbitrary depth with nothing checking it at all. Consuming such a value with explode_aliases, sort, unique, ==, group_by, "a * b", or simply using it as a mapping key (build.rs:144 inserts into an IndexMap, which hashes the key) drives recursion to that depth. A stack overflow in Rust is a SIGSEGV/abort, not a catchable panic. The emit path is the one place that is protected - emit/mod.rs validate_value walks iteratively and calls check_depth before to_yaml/to_json recurse - which shows the correct pattern is already understood and simply was not applied to the value type's own traversals.

Give the recursive traversals the same treatment validate_value already has. Either convert explode_aliases, deep_merge, Display, and Ord/Eq/Hash to explicit worklists like drop_values, or thread a depth counter through the ones that return Result (explode_aliases, deep_merge) and bound the ones that cannot (Ord/Eq/Hash/Display) by making the builder enforce a *value* depth budget: track resulting depth when an alias is expanded in build.rs so check_depth reflects post-expansion tree depth rather than event nesting. Independently, cap depth for filter-constructed values at the point jaq hands an output back to the driver, since nothing bounds them today.

Input errors round-trip through String, collapsing every class to InputParse (exit 5)

Related: halt(code) exit status truncates to u8, mapping halt(256) to success Effort: small12-mo commits
moderate

YgError is documented at error.rs:28 as "partitioned by their CLI exit-code class", and exit_for (commands/query.rs:610) maps InputRead to 2 and InputParse/Runtime to 5. The input stream defeats that partition: every per-input error is stringified at engine.rs:228 to satisfy jaq's RcIter<Result<V, String>> contract, then reconstructed unconditionally as YgError::InputParse at engine.rs:246 ("let input = input.map_err(|error| E::from(YgError::InputParse(error)))?;"). An InputRead error therefore exits 5 instead of 2. This is reachable in normal use. cmd_query pre-checks paths with fs::metadata (validate_input_paths, commands/query.rs:435), which succeeds on a file the caller cannot open; the later read_to_string in collect_inputs (commands/query.rs:473) then fails with EACCES, producing YgError::InputRead, which the round-trip converts to InputParse. "chmod 000 f.yaml; yg . f.yaml" exits 5 ("the document was malformed") when the contract says 2 ("the file was unavailable"). Anything scripted against yg's exit codes cannot distinguish an unreadable file from a broken document. The blanket "impl From<String> for YgError" at error.rs:81-85 is what makes the lossy conversion invisible: any bare String silently becomes InputParse, so the compiler cannot flag the place where the class was dropped.

Carry the class alongside the message rather than reconstructing it. Keep a side channel: stash the original YgError in a RefCell on RunCtx keyed to the input being yielded, and on failure at engine.rs:246 restore the stored error instead of wrapping the string. Deleting "impl From<String> for YgError" would force every remaining call site to name its class explicitly, and a CLI test asserting exit 2 for an unreadable-but-present file would pin the behavior.

runtime_limits guards string repeat but not concatenation or sequence growth

Related: Recursive YamlVal traversals have no depth bound; only the Drop path is iterative Effort: small12-mo commits
moderate

runtime_limits.rs exists so that jaq trait methods, which never receive RunCtx, can still see the run's ResourceLimits through a thread-local activated in run_filter_with_null_input (engine.rs:227). The guard itself is real and correctly scoped - the Guard's Drop restores the previous value - but it is consulted on only three paths in the whole crate: string repeat in Mul (ops.rs:130, "crate::runtime_limits::check_scalar_size(size)") and the two sparse-array assign paths in map_index (valt.rs:202, valt.rs:266). The adjacent growth operators are unchecked. "Str + Str" (ops.rs:65) allocates a fresh String of any size, and "Seq + Seq" (ops.rs:67) extends without consulting check_collection_size. Because "*" is guarded and "+" is not, the coverage is easy to mistake for complete. With the filter treated as untrusted input, "yg -n 'reduce range(40) as $i (\"x\"; . + .)'" doubles the allocation forty times with nothing to stop it; Rust's default allocation-failure handler aborts the process rather than unwinding, so there is no error to report and no exit code to interpret. The same applies to "reduce range(40) as $i ([0]; . + .)" for sequences. Under --trusted the checked paths are disabled too (max_scalar_bytes and max_collection_size are both None), but that is an explicit opt-in; the gap is visible under the default moderate profile, which does cap both.

Call crate::runtime_limits::check_scalar_size on the summed length before the concat at ops.rs:65 (checked_add on the two lengths first), and check_collection_size on left.len() + right.len() before the extend at ops.rs:67. Then sweep the remaining constructors that can grow a value - ValT::from_map (valt.rs:33), YamlVal::seq via FromIterator (value.rs:687), and map_values (valt.rs:142) - for the same omission, and add a test per operator so the guard's coverage is asserted rather than assumed.

ValT::into_string turns an emit error into a plausible string value

Related: Input errors round-trip through String, collapsing every class to InputParse (exit 5) Effort: small12-mo commits
moderate

into_string backs "tostring" and string interpolation. to_json can fail for two reasons that are entirely input-driven: EmitError::Limit, and EmitError::DuplicateJsonKey when two distinct YAML keys collapse to the same JSON name. On either failure the error text is wrapped as an ordinary YamlVal string and flows onward as data: $ printf '{1: "x", "1": "y"}\n' | yg '. | tostring' "<yg: JSON object key \"1\" would be duplicated after string conversion>" exit=0 Note which limits apply here, because it is not the run's: into_string renders with EmitOpts::compact(), which inherits EmitOpts::default(), whose limits are hard-wired to LoaderConfig::moderate().limits (emit/mod.rs:61). The invocation's own profile never reaches this render, so --strict neither tightens nor applies - the cap is moderate's regardless. The reachable Limit trigger is moderate's max_depth of 256, checked by validate_value before rendering: $ yg -n 'reduce range(300) as $i (null; [.]) | tostring' "<yg: depth 257 exceeds maximum of 256>" Either way the result is exit 0 with nothing on stderr - and a downstream "| fromjson", or a write into a config file, then consumes the error message as a value. jaq's trait signature ("fn into_string(self) -> Self") genuinely forbids propagating a Result here, so there is no clean local option. But silently substituting an error string for data is the worst of the available choices: it is indistinguishable from a legitimate value and the exit code still reports success. Note that the sibling native "tojson" (funs.rs:78) can propagate and does, so the two spellings of the same operation disagree about whether a limit breach is fatal.

Record the failure in a thread-local next to runtime_limits::ACTIVE (or a RefCell on RunCtx) when into_string falls back, and have run_filter_with_null_input check that flag after each output and convert it into a YgError::Runtime. Alternatively render into_string with ResourceLimits::none(), since an internal string conversion is not what max_output_bytes is about - that removes the Limit branch entirely and leaves only DuplicateJsonKey to surface.

halt(code) exit status truncates to u8, mapping halt(256) to success

Related: Input errors round-trip through String, collapsing every class to InputParse (exit 5) Effort: trivial12-mo commits
advisory

jaq surfaces "halt(code)" as an i32 (error.rs:58-66 extracts it via get_halt). exit_for casts it with "as u8", which silently wraps: halt(256) and halt(512) both exit 0, and halt(-1) exits 255. report() (commands/query.rs:591) additionally suppresses the diagnostic for Halt, so a filter that deliberately requests a failure exit can produce a completely silent success. A caller writing "yg 'if .bad then halt(256) else . end' || alarm" never fires the alarm. Only exact multiples of 256 collapse to success — halt(400) truncates to 144, which is still a failure status — so the blast radius is narrow, but it is silent where it lands. This matches jq, whose halt calls exit() and is truncated by the OS the same way, so the behavior is defensible as compatibility rather than a bug. It is flagged because it is the only place in this function where an exit code is produced by a lossy cast rather than a literal, and nothing in the code or the r[impl cli.exit] annotations records that the truncation is intentional.

Either clamp explicitly and document the intent - "u8::try_from(*code)" with a fallback and a comment naming jq compatibility as the reason - or reject out-of-range halt codes where YgError::Halt is constructed so the filter author gets a diagnostic instead of a wrapped status. A test pinning halt(256) to whichever behavior is chosen keeps the decision from drifting.

Parser invariant violations are reported as BuildError::Limit

Effort: trivial12-mo commits
advisory

BuildError::Limit is documented as "A loader resource limit was exceeded" (error.rs:23-25). Two sites use it for something else entirely: an unexpected event kind mid-node (build.rs:172) and a truncated event stream (build.rs:243, "BuildError::Limit(\"unexpected end of parser event stream\")"). Both are parser-contract violations, not resource exhaustion. Choosing an error over a panic here is the right call - neither site can abort the process - but it means a caller matching on BuildError cannot distinguish "your document exceeded the configured limits, retry with --trusted" from "the parser and builder disagree, file a bug". BuildError is public and converts into YgError::InputParse, so the misclassification reaches the user as advice that will not help.

Add a distinct variant - BuildError::UnexpectedEvent(String) or similar - for the two invariant sites, leaving Limit to mean only what its doc comment says. The crate is pre-release with no published API, so adding a variant costs nothing.

-i aborts on any file whose owner or group the caller cannot reproduce

Effort: trivial12-mo commits
advisory

run_in_place calls preserve_owner unconditionally before persisting (commands/query.rs:235). chown(2) to a uid other than your own is root-only, and setting a gid you are not a member of also fails, so "yg -i" errors out for any file owned by another user or carrying a foreign group - even when the directory is writable and the edit would otherwise succeed. Comparable tools do not behave this way: sed -i and the usual jq sponge idiom simply leave the replacement owned by the caller. The failure is clean. It happens before persist, and the NamedTempFile is dropped and deleted, so nothing is corrupted and no partial write escapes. What makes it worth flagging is the inconsistency: this is the only metadata-preservation step in run_in_place that is fatal. The sibling hard-link case emits a warning and continues (warn_if_hard_linked, commands/query.rs:312), and set_permissions runs afterward. Failing closed on ownership may well be the intended policy, but nothing states it and there is no way to opt out.

Decide the policy explicitly and make it consistent with warn_if_hard_linked: either warn and continue when chown returns EPERM (documenting that the replacement will be owned by the caller), or keep the hard failure and say so in the -i help text and in the error message, e.g. "refusing to change ownership of {path}; re-run as its owner". Matching on the error kind is worth doing either way - a genuine I/O failure should stay fatal regardless of which policy is chosen.

No change required for correctness. If these are touched anyway, prefer making the invariant structural - have block_collection take a type that can only hold a Seq or Map, and have resolve_scalar return a scalar-only type - so the unreachable arm disappears instead of being asserted. At minimum, a doc comment on each naming the caller-side check that upholds it would keep the coupling visible.

This surface is the audit's center of gravity. The findings are not about missing error handling — thiserror is used properly and the ? propagation is consistent — but about where the bounds live. Recursion over the value tree has no depth ceiling, growth operators sidestep the limits that do exist, and a limit-labeled error is used for what are actually builder invariant violations, which will make real limit breaches harder to diagnose. The in-place edit path is otherwise well built; its one rough edge is treating a chown failure as fatal after the content is already correct.

The Allocation and Throughput Surface

The query path trades yamalgam's zero-copy discipline for metadata fidelity, and that trade — reasonable in itself — is made silently and then compounded by per-scalar allocations in the resolver and emitters.

The event-to-YamlVal builder is the hot path for parsing: it runs once per node for the whole document. The scalar arm at build.rs:102-111 calls resolve_scalar(&value, ...) to produce Data — which for the overwhelmingly common string case is Data::Str(Rc::from(text)), one heap allocation plus a byte copy — and then passes Some(&value) into finish(), whose raw: raw.map(Rc::from) builds a second, independent Rc<str> holding byte-identical content. The stack-safe Drop for YgMap heap-allocates on every mapping destruction, including tiny maps

Effort: small12-mo commits
advisory

The iterative Drop impls exist to prevent stack overflow on deeply nested values, which is the right call. But YgMap's version pays for it on every drop: the collect::<Vec<_>> in drop_values must allocate a fresh 2n-element Vec and move every key and value into it. The cause is the source iterator, not the adapter — the Vec::from_iter allocation-reuse specialization applies only when a vec::IntoIter<T> is collected back into Vec<T>, and YgMap's source is IndexMap::into_iter() (indexmap::map::IntoIter yielding (YamlVal, YamlVal) pairs), a different iterator type with a different item type from the YamlVal being collected. Removing the flat_map would therefore not enable reuse; the allocation is unavoidable at this call site as structured. YgSeq's path is fine by comparison — value.rs:113 passes a real Vec<YamlVal>, so the input is a plain vec::IntoIter and collect reuses the existing buffer. That contrast holds, but the reason is the IndexMap source. jaq creates and destroys mappings constantly during evaluation, and the dominant real shape is a small map of one to five entries where a recursive drop would allocate nothing. There is no small-size fast path, so a two-entry temporary map pays a malloc and a free purely for a depth guard it can never need.

Add a shallow fast path: if the map is below a small entry threshold, or if no entry's data is a Seq or Map, let the entries drop normally and return before touching the stack. The taken IndexMap then drops normally, and any nested Rc<YgSeq>/Rc<YgMap> still hit their own iterative Drop impls, so the stack-overflow property is preserved. Alternatively drain into a thread-local reusable stack buffer so the allocation amortizes across all drops in a run.

Record the trust decision where it can be reviewed — either a comment on this dependency line or a short note in the M10 implementation-notes doc naming rust-zstd and leakguard as accepted transitive risk and why. Separately, check whether librebar can make rust-zstd optional so consumers that do not need compressed log rotation or diagnostics bundles can opt out; that fix belongs in librebar, not here. Note that dropping the diagnostics feature is only a partial move: it removes leakguard and tar, but NOT rust-zstd — the decompressor this finding is most concerned about — because librebar declares rust-zstd under logging as well (logging = [dep:tracing-subscriber, dep:tracing-appender, dep:serde_json, dep:directories, dep:rust-zstd]), and logging is explicitly requested here and is itself a prerequisite of diagnostics. Removing rust-zstd requires the upstream change described above.

Effort: trivial
note

The audit context flags an apparent contradiction: cargo-audit reports RUSTSEC-2023-0051 (dlopen_derive 0.1.4, unmaintained) as an allowed warning, while the captured deny.txt says the allowlist entry "no crate matched advisory criteria". Both are correct and the difference is the feature graph. cargo-audit scans Cargo.lock directly and is feature-agnostic, so it sees dlopen_derive 0.1.4 because yamalgam-bench's optional yamlstar peer keeps it in the lock. cargo-deny walks the resolved metadata graph, where yamlstar is off unless features are enabled. I reproduced both branches: cargo deny --all-features --config .config/deny.toml check emits no advisory-not-detected warning and reports "advisories ok, bans ok, licenses ok, sources ok", while cargo deny --config .config/deny.toml check (no feature flag) emits warning[advisory-not-detected] ... no crate matched advisory criteria pointing at line 57. The captured deny.txt therefore came from a run without --all-features, and the audit context's claim that the corrected invocation still reports the unmatched entry does not hold — with --all-features the entry matches cleanly. The chain is genuine and correctly scoped (yamlstar 0.1.18 -> dlopen 0.1.8 -> dlopen_derive 0.1.4, benchmark-only, never in the yg binary), so there is no security gap. What exists is a policy file whose correctness depends on an invocation flag that is not written down anywhere. Scope note: .config/deny.toml is not in the M10 changed-file manifest, so this predates the milestone and is reported only because it was explicitly asked for.

Pin the invocation so the config and the command agree. Either standardise on cargo deny --all-features --config .config/deny.toml check in CI and the justfile so the ignore entry is always exercised, or scope the entry with cargo-deny's per-crate ignore form so it does not warn when yamlstar is absent. Whichever way, the flag requirement belongs in a comment beside the entry — the current comment explains why the advisory is ignored but not why the entry sometimes appears dead.

The dependency choices are sound in kind — jaq is the right engine, librebar is already the workspace's CLI substrate — but they were taken with defaults, and the defaults are expensive. The exact pins on jaq are a defensible reproducibility choice that carries a patch-response cost worth acknowledging.
